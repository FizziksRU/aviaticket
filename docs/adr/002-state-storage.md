# ADR-002. Где хранить состояние

**Статус:** предложение.
**Дата:** 2026-11-03.

## Контекст

Состояние разбросано:
- сессии диалога, последние выдачи (`ResultStore`), множество `busy`, кэш и замки guard, пул устройств DroidHub — в памяти процесса (`dialog.py:145`, `store.py:40`, `guard.py:57-59`, `droidhub.py:17-23`);
- пользователи, подписки, история цен — три отдельных SQLite-файла в режиме `journal_mode=delete` с синхронными вызовами из event loop.

Рестарт стирает выдачи и сессии. Второй процесс бота невозможен: getUpdates допускает одного потребителя, а пул телефонов и кэш у каждого процесса свои.

## Решение

- **Ступень 10–50:** один процесс. Три базы объединить в одну SQLite в режиме WAL. Запись идти через один поток (`asyncio.to_thread` с очередью) или `aiosqlite`. Добавить номер версии схемы и миграции. Сессии и снимки выдачи хранить в той же базе с TTL, чтобы рестарт и деплой не обрывали диалоги. Добавить ретеншн `price_history` и `sub_prices` (30–90 дней).
- **Ступень 100:** Postgres (сессии, пользователи, подписки, история, очередь задач по ADR-001) и Redis (кэш выдачи по маршруту, дате и сайту с TTL по источнику; общие замки «сайт × телефон»). Бот переходит на webhook и работает без состояния, поэтому процессов может быть несколько.

## Альтернативы

- **Сразу Postgres.** Правильно для ступени 100, но для одного процесса это лишний сервис и бэкапы. SQLite WAL выдерживает нагрузку 50 человек с запасом: в симуляции база не узкое место.
- **Оставить три SQLite.** Нет транзакций между пользователями и подписками, три набора миграций.
- **Redis как основное хранилище.** Хорош для кэша и очереди, плох для истории цен и отчётов.

## Последствия

- Деплой без потери выдач и сессий; graceful shutdown (ветка `scale-audit-dialog`) дожидается текущих поисков.
- Миграции становятся частью релиза.
- На ступени 100 появляется инфраструктура: Postgres и Redis (managed или на том же VPS), их бэкапы и мониторинг.
