# 02. DroidHub / pool-avia: как работает и сколько стоит

Замеры 2026-11-03 20:01–20:24 UTC через MCP `pool-avia` (тот же DroidHub, что у бота). Параметры запросов совпадают с `droidhub.py`: `url` из `sites.build_url`, `wait_seconds`, `capture_json` и `wait_for` из `sites.yaml`. Ответы разобраны **кодом бота**: `droidhub._fetch_device_snapshot` через `httpx.MockTransport`, затем `pipeline._process_snapshot` (`tools/phase2.py`). Сырые строки лежат в `docs/audit/phase2_runs.csv`, снимки в `debug/samples/` (в git не входят). Журнал запросов: `docs/audit/phone_budget.log`.

Маршруты: near — MOW→LED 20.11.2026 (через 16 дней), far — MOW→AER 22.01.2027 (через 80 дней), rt — MOW⇄LED 20.11–27.11.

**Ограничения выборки.** На каждую пару «сайт × телефон» 2–4 замера, поэтому p95 здесь фактически равен максимуму. Это оценка порядка величин, а не статистика. Боевой бот в это время, возможно, тоже работал на телефонах: на redmi была открыта вкладка Ozon, которую я не открывал.

## 1. Контракт API (восстановлен по клиенту и ответам)

`POST {DROIDHUB_URL}/api/devices/{device_id}/fetch_page`, заголовок `Authorization: Bearer <token>`.

| Поле запроса | Что делает | Как использует бот |
|---|---|---|
| `url` | открыть в Chrome телефона | из шаблона `sites.yaml` |
| `wait_seconds` | верхняя граница ожидания | `phone_wait_seconds`, клиент режет до 1–60 (`droidhub.py:184`) |
| `capture_json` | подстроки URL XHR-ответов, которые надо вернуть | `phone_capture_json` |
| `wait_for` | подстрока в теле перехваченного ответа, признак конца выдачи | только у aviasales |
| `max_chars` | обрезка `text` (JSON не режется) | 200 000 |
| `wait_full` | ждать `wait_seconds` целиком | **бот не передаёт** |

Ответ 200: `{url, title, text, truncated, captcha, json_responses:[{url, status, body}], finished, seconds}`.
- `seconds` — время на стороне сервера. Именно его я и замерял.
- `url` — итоговый адрес, может содержать `searchId=…` или `#empty` (yandex до конца опроса партнёров).
- `finished` эмпирически означает «условие выполнено»: найден `wait_for` или, если его нет, JSON перехвачен и страница успокоилась. Это не гарантия данных. Встретилось `finished=true` при пустом `json_responses` (yandex RT на realme) и `finished=false` при 7 перехваченных ответах (aviasales RT упёрся в 45 с). Бот выставляет `partial = not finished` (`pipeline.py:229`), то есть `finished` правильно трактовать как «полнота», а не как «успех».
- `captcha=true` → бот бросает `RuntimeError("сайт показал капчу на телефоне")` (`pipeline.py:227-228`). За 38 запросов капч не было.

Ошибки (по коду клиента `droidhub.py:208-218`): 401/403 — токен (не повторяется), 429 — «очередь droidhub занята», 502 — «телефон недоступен или страница не открылась». На 429 и 502 клиент пробует следующий телефон из кандидатов. За 38 запросов 429 не было ни разу: я не отправлял больше одного запроса на телефон одновременно. Через MCP onetwotrip на redmi 3 раза из 3 вернул непрозрачное `Error executing tool fetch_page`, при этом экран redmi показывал рабочий стол, без зависшей вкладки.

Очереди. У бота своя очередь: `asyncio.Lock` на телефон, пул `_busy_devices` с round-robin, а сверху lock сайта в guard. У сервера тоже есть очередь, о ней говорит 429, но её глубина и политика неизвестны. Итого очереди двойные, и о чужой нагрузке (боевой бот на тех же телефонах) клиент узнаёт только из 429.

Прочее: `GET /api/devices` (MCP `list_devices`) отдаёт `id, name, online, battery, temperature, screen_on, last_seen, error`. Клиент на каждый запрос создаёт новый `httpx.AsyncClient` (`droidhub.py:201`), без keep-alive. HTTP-таймаут равен `wait_seconds + 60`.

Выводы:
1. **realme в 1,5–3 раза быстрее redmi** на всех сайтах, которые работают на обоих: kupibilet 6 и 13 с, tutu 5,5 и 14 с, yandex 7 и 13 с.
2. **Надёжность зависит от пары «сайт × телефон», а не только от сайта.** ozon не работает на realme, но работает на redmi. aviasales и onetwotrip — наоборот. При `phone: auto` round-robin примерно в половине случаев отправляет ozon и aviasales на «не тот» телефон.
3. Без `wait_for` DroidHub возвращает ответ, как только JSON перехвачен, и не ждёт `phone_wait_seconds`. Поэтому реальное время в 2–5 раз меньше лимитов из `sites.yaml`. Но если JSON не перехватился, телефон ждёт лимит целиком: 31 с у ozon и onetwotrip, 46 с у aviasales.
4. yandex **всегда partial**: бот забирает первый чанк, в котором опрошено 2 партнёра из 20 (`progress.current=2, all=20`, `cont=1`).
5. tutu на телефоне отдаёт 10 офферов. `replay_post` (cheapest, limit 100) работает только в Playwright-пути. На near-маршруте desktop Playwright (фаза 1) дал минимум 2 379 ₽, а телефон — 2 442 ₽.

## 3. Стоимость одного поиска в телефонных секундах

Формула: E[T_поиска] = Σ по сайтам E[T_сайта]. Для сайта с `auto` и двумя телефонами E = ½·E_realme + ½·E_redmi. Для промаха E_промах = T_лимит + T_повтор: `ParserEmptyError` даёт один повтор через 3 с (`pipeline.py:280-293`), повтор берёт следующий телефон по round-robin.

| Сайт | Маршрутизация | E, с (в одну сторону) | Из них realme | Из них redmi |
|---|---|---|---|---|
| aviasales | auto | 0,5·22,5 + 0,5·(⅓·37,7 + ⅔·(46,5+22,5)) = **40,5** | 18,8 | 21,8 |
| kupibilet | auto | 0,5·6,4 + 0,5·13,3 = **9,9** | 3,2 | 6,7 |
| tutu | realme | **5,4** | 5,4 | — |
| yandex_travel | realme | **7,1** | 7,1 | — |
| onetwotrip | realme | **7,8** | 7,8 | — |
| ozon_travel | auto | 0,5·(31,2+9,2) + 0,5·9,2 = **24,8** | 15,6 | 9,2 |
| **Итого OW** | текущий конфиг | **≈ 96 с** | **≈ 58 с** | ≈ 38 с |
| **Итого RT** | текущий конфиг | **≈ 190 с** (aviasales 46–92, onetwotrip 2×31 промаха) | **≈ 150 с** | ≈ 40 с |
| OW, оптимальная привязка | aviasales, onetwotrip, yandex → realme; ozon, kupibilet, tutu → redmi | **≈ 74 с** | 37,4 | 36,6 |

Отсюда потолок по телефонам при идеальной упаковке и без кэша:
- **текущий конфиг: realme тратит ~58 с на OW-поиск → ≤ 62 OW-поиска/ч** на оба телефона (redmi при этом загружен на ~65%); на RT ~150 с → **≤ 24 RT-поиска/ч**;
- **оптимальная привязка: ~37 с на телефон → ≤ 96 OW-поисков/ч** на 2 телефона.

Проверка гипотез:
- **Гипотеза 2** («190–220 с на поиск») **для поиска в одну сторону не подтверждается**: ~96 с при текущем конфиге, ~74 с при оптимальном. Сумма `phone_wait_seconds` (190 с) — это верхняя граница, а не типичное время. **Для туда-обратно подтверждается**: ~190 с, потому что onetwotrip и aviasales промахиваются.
- **«Повтор при ParserEmptyError удваивает стоимость» подтверждается**: промах ozon на realme 31 с + повтор; aviasales на redmi 46,5 с + повтор. На такие промахи приходится ~40% телефонного времени OW-поиска (≈ 38 из 96 с).
- **Гипотеза 3** (realme — узкое место, redmi простаивает) **подтверждается с поправкой**: realme тратит ~58 с из ~96 на каждый поиск (60%). Причина не только в жёсткой привязке трёх сайтов: `auto` ещё и гонит на realme ozon, который там не работает.

## 7. Рекомендации

1. **Привязка по замерам, а не `auto` везде:** aviasales → realme, onetwotrip → realme, ozon_travel → redmi. kupibilet, tutu и yandex работают на обоих, их оставить `auto`, но с предпочтением быстрого телефона. Гипотеза «`phone: auto` везде» **отклоняется**: для ozon и onetwotrip это прямой вред.
2. **Учитывать здоровье пары «сайт × телефон»:** скользящая доля успехов, и при серии промахов телефон временно исключается для этого сайта. Повтор после `ParserEmptyError` делать на другом телефоне, а не наугад по round-robin.
3. **yandex:** `wait_for '"cont":null'` даёт полную выдачу. Если 39 с телефонного времени на сайт — это дорого, компромисс такой: `wait_for` + `wait_seconds: 25`, взять все чанки, которые успели прийти (`finished=false`, но офферов уже в разы больше).
4. **Снизить `phone_wait_seconds`** для быстрых сайтов до 15–20 с: это сокращает цену промаха вдвое.
5. **tutu:** в телефонном пути нет `replay_post`, поэтому и сортировки cheapest. Это кандидат на прямой HTTP-реплей `/avia/offers/v2` с куками сессии телефона (вариант 4 в фазе 5).
6. **Кандидаты на прямой JSON без телефона:** kupibilet (`/frontend_search`, ответ 100–200 КБ), tutu (`/avia/offers/v2`), ozon (`aviaSearchResult`), yandex (`/api/avia/search/results?cont=…`). Все они — обычные XHR-API. Насколько их защищает антибот при прямом вызове, не проверено. Это следующий шаг, его нельзя делать нагрузкой на живые сайты.
7. **DroidHub:** если на странице уже видна выдача, а JSON так и не перехвачен, сдаваться через N секунд, а не ждать лимит. Отдавать отдельный код «нет JSON» вместо `finished=false`. Клиенту держать один `httpx.AsyncClient` на процесс.
8. **onetwotrip на redmi:** разобрать причину ошибки MCP по логам DroidHub (мне они недоступны), до тех пор оставить onetwotrip только на realme.
